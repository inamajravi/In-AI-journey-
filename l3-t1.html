Config-driven, layered AI-system architecture

Level 3 · Topic 1 of 6

Why it matters

You already build this way. Naming and formalising the pattern is what turns it into architect-level language.

Core concepts

  • Layers: API/edge, orchestration, model gateway, retrieval/data, tools, evaluation and observability. Each with a clear responsibility.
  • Model gateway: one place that handles model choice, keys, retries, timeouts, logging and cost tracking. Application code never calls a model directly.
  • Config-driven: prompts, model names, thresholds, tool lists and list mappings live in versioned config, not code, so changes are reviewable and reversible.
  • Deterministic core, AI at the edges: use code for rules and decisions that must be auditable; use the model for language, summarisation and ambiguity.
  • Portability: keep provider-specific details behind an interface so switching models is a config change plus an eval run.

Hands-on exercise

Draw your sanctions platform as layers. For each layer, write its single responsibility and one thing it must never do. Identify where a model gateway would remove duplication.

Self-check

  1. Why should application code never call the model directly?
  2. What belongs in config versus code?
  3. Where is the line between deterministic logic and LLM behaviour in your system?

Messages API: streaming, tool use, structured JSON

Level 1 · Topic 2 of 4

Why it matters

The Messages API is the foundation under every framework. If you understand the raw request/response shape, frameworks stop being magic.

Core concepts

  • Request shape: model, max_tokens, optional system, and a messages array of alternating user/assistant turns. Responses return a list of content blocks, not a plain string.
  • Streaming returns tokens as they are generated (server-sent events). Use it for chat UIs so users see progress; skip it for backend batch jobs where you only need the final result.
  • Tool use: you describe tools (name, description, JSON input schema). The model may respond with a tool_use block and stop_reason 'tool_use'. Your code runs the tool and returns a tool_result in the next user turn. The model never executes anything itself.
  • Structured output: define a tool whose input_schema is the JSON shape you want and force or strongly prompt its use. You get schema-shaped data instead of free text to parse.
  • Why this beats regex: free-text parsing breaks on phrasing changes; a schema is a contract your code and the model both follow, and you can validate it.
  • Errors to handle: rate limits (429), overloaded responses, max_tokens truncation, and invalid tool input. Retry with backoff; validate before acting.

Hands-on exercise

Write down the JSON schema for a screening result: {matched: bool, score: number 0-1, list: string, reasoning: string}. Define it as a tool, call the API with a sample name, and check that the tool_use input validates against your schema in code.

Self-check

  1. What does the model return when it wants to call a tool, and who actually runs the tool?
  2. Why is a tool schema a better output contract than 'reply in JSON please'?
  3. When would you not stream?
  4. How do you handle the model returning input that fails your validation?
